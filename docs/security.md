# Desktop control security

Pairing grants a website screenshots, visible window titles, pointer control, and keyboard control over the current Windows desktop. Only approve origins you trust. The bridge shows the requesting origin in a native Windows confirmation, with Deny selected by default. It grants no access until you approve.

The bridge binds only to 127.0.0.1 on one of three reserved ports, 17373, 17374, or 17375, and accepts exact configured website origins. It rejects missing origins, Origin:null, a Host different from its bound endpoint, and untrusted origins. CORS never uses a wildcard. Discovery is read-only and limited to those three loopback ports. Paired HTTP requests and WebSocket events remain on the selected endpoint. OPTIONS responses include the older Private Network Access compatibility header. The browser remains responsible for its loopback network permission prompt; the bridge cannot grant or bypass that permission.

Approval creates a random 256-bit bearer token, held in memory. It belongs to one exact origin. Pairing again revokes the prior session. Sessions remain enabled until unpairing, native STOP, replacement, or process exit. There is no forced 60-second lease. A token is never a query parameter. WebSocket authentication happens in the first message and expires after five seconds if absent.

Press Ctrl+Alt+Escape to revoke all sessions immediately. Close the visible console to stop the bridge entirely. The hosted STOP button must call `/v1/unpair`; aborting a fetch alone does not cancel Windows input. The native input executor checks session validity before each input batch and throughout drags. Revocation shares a lock with input dispatch, so a request cannot pass the check and then begin sending input after revocation. If cancellation occurs while a mouse button or modifier is down, the bridge still releases it. These release events are cleanup, not new actions.

The emergency hotkey must register successfully before the server starts. If another program owns it, the bridge refuses to start. Tokens are not written to logs or disk. Native logs record event IDs, timestamps, and event types, not typed text. The hosted event history can contain screenshots and typed content. Treat exports as potentially private.

Scopes are screen.read, pointer, keyboard, and windows.read. Clipboard access is not implemented or granted. Input requires the corresponding scope, and observations require screen.read. Strict payload validation rejects extra fields. Limits bound input length, drag duration, hotkey length, screenshot size, watch count, request rate, and action rate. Stop requests bypass the request rate limit. Pair prompts have a separate six-per-minute limit and only one prompt can be open.

The bridge has no shell, PowerShell, subprocess, filesystem, registry, or arbitrary network execution endpoint. Windows itself still interprets keyboard and mouse actions. A trusted agent could type into a terminal that you leave focused, so a visual-only protocol is not an application sandbox. Review the selected target and expected action before starting an external agent.

The executable runs with ordinary user privileges. Windows may reject input into elevated applications, lock screens, or secure desktops. Lense reports these input failures. Do not run the bridge as administrator to bypass this boundary. Window capture records the visible desktop rectangle; overlapping windows may appear in it. Keep the target visible and verify screenshots before acting.

All automated Rust API tests use MockInputExecutor. They do not send desktop input or show native consent. The included native smoke procedure is manual and separate. Browser mock-bridge tests do not prove that Windows input succeeded on a real desktop. A physical test must verify pointer mapping on your displays, Unicode typing, scroll direction, hotkeys, capture, and emergency stop.

Norton quarantined the unsigned 1.0.1 download as IDP.Generic. Distribution is paused pending review. Keep quarantined copies in quarantine. Public packaging now requires matching version metadata, clean build provenance, and a valid Authenticode signature from the expected certificate. Candidates remain separate and marked not approved. A matching hash or valid signature does not establish that an executable is safe. See the [antivirus review](antivirus-review.md).

The API cannot authenticate other applications already running as your Windows user. A local program can fabricate HTTP Origin headers. The native consent prompt is the additional boundary for creating a control session. HTTPS, the exact origin allowlist, native consent, and keeping tokens out of persistent storage protect browser access; they do not defend against malware already running with your account's privileges.
